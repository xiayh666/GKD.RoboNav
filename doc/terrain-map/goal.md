# 骨架目标

## G1 - 可统一构建的纯 Rust 库
- 用户故事：在讨论地形算法前，先有独立库及工程构建入口。
- 成功标准：Cargo 可编译 terrain-map；容器 colcon 识别 terrain_map 为 cmake 并与其他工程模块一起构建成功。
- 依赖：已有 Cargo 工作区、ros2 容器中的 Rust 工具链。
- 非目标：本轮不实现地图、特征或通行性算法，不承诺尚未确定的 API。

## G2 - 可验证的体素与并发运行底座
- 用户故事：雷达高吞吐输入可在有界CPU资源下处理，不让异步调度被计算阻塞，并保持地图和人工命令版本一致。
- 成功标准：射线空闲/占用/未知、负坐标和边界、过期/窗口、拒绝事务、历史快照、串并行等价均通过测试；current_thread运行时的背压、确认、关闭和watch语义通过测试；实际容器构建通过；1/2/4工作线程吞吐结果留档。
- 依赖：G1；Tokio及Rayon；Rust ≥1.85。
- 非目标：本阶段不实现地形特征、隧道自动识别、通行性或ROS桥接，不用人工提示冒充自动结论。

## G3 - 复用Point-LIO观测而非定位缓存语义
- 用户故事：地形模块复用已变换的上游体素观测和位姿，独立维护环境证据，不因定位缓存筛点/淘汰遗漏或删除地形。
- 成功标准：源筛点前输出、逐点原点及源键复用、LRU隔离、会话重置/丢序/晚加入重同步、标注会话保护通过测试；已提交轨迹回放保持字节一致。
- 依赖：G2和Point-LIO同步核心。
- 非目标：本轮不改滤波/iVox数学，不实现地形、隧道、ROS桥接或完整LIO在线调度服务。

## G4 - 接入链路性能与资源验收
- User story：判断当前Point-LIO观测导出到地形地图维护在10Hz输入下是否跟得上，并明确内存、背压和容量边界。
- Success criteria：ros2容器Release顺序运行1k/10k/20k点各600帧、10k点连续旋转3000帧；逐帧留存LIO、提交、完成、固定节拍延迟；采样CPU/RSS；隔离观测分组和地形提交；超速输入不静默丢序；移动窗口/TTL/默认20万格容量边界有断言证据。明确记录通过与不通过，不把“完成测量”当作“所有指标达标”。
- Dependencies：G3观测增量接口。
- Non-goals：本轮不调整里程计算法或掩盖超时；尚未实现的地形/隧道分析没有准确率可测，实机驱动和ROS端到端延迟需实际传感器输入。
